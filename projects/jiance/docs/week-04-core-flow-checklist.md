## 三、唯一的两条控制台报错（**不算 bug**，但要知道）

跑边界用例时，控制台会出现：

```
Failed to load resource: the server responded with a status of 400 (Bad Request)
```

**这是浏览器对任何 4xx 的固定行为，躲不掉**，而且背后的响应是**设计内的**：

```json
{"ok":false,"data":null,"error":{"code":"bad_request",
 "message":"金额太大了，最多能记 9999999999.99","field":"amount"}}
```

服务端主动拒绝 + 给了中文原因 + `field: amount` 指到哪个框；前端**确实把它显示出来了，还把输入框标红了**。

> ⇒ **「控制台有红色报错」不等于「有 bug」**。判断要看：这句话是谁说的、有没有传达给用户。

### 改了什么

`projects/jiance/src/pages/Resume.css` 末尾新增一段集中的「长串兜底」规则，
给**所有承载用户 / 模型文字的**元素加 `overflow-wrap: anywhere`：
简历纸里 8 个（`.resume-name` / `.resume-role` / `.resume-contact` / `.item-period` /
`.item-role` / `.item-org` / `.item-content` / `.item-result`）
+ 回填区 4 个（`.rewrite-who` / `.rewrite-orig` / `.rewrite-cand-text` / `.rewrite-prev-text`）。

> **为什么是 `anywhere` 而不是更常见的 `break-word`**：`break-word` 只在「这一行排不下」时才断，
> 而且**不算进元素的最小内容宽度**；在 flex / grid 布局里最小宽度仍会被长串撑住 → **照样溢出**。
> `anywhere` 把断点计入最小内容宽度，才是真能挡住的那个。

### B-2 · 输入上限（治源 · 2026-10-12 晚追加）

秋鹰师回「**要**」，采用建议值。`Entry.jsx` 四个文本字段加 `maxLength`：

| 字段 | 上限 | 界面提示（placeholder） |
|---|---|---|
| `content` 内容 | **120** | `做了什么（动词开头，120 字内）` |
| `result` 成果 | **60** | `量化更好（选填，60 字内）` |
| `org` 公司 | **40** | `选填（40 字内）` |
| `role` 职位 | **40** | `选填（40 字内）` |

**实测 16/16 全过**（`Temp/day24_maxlen_e2e.js`，浏览器真跑）：

| 验什么 | 结果 |
|---|---|
| 真实键入 150 / 60 / 60 / 80 字 → 截到上限 | ✅ 四个字段全过 |
| **真实 `Ctrl+V` 粘贴** 150 / 60 字 → 截到上限 | ✅（这才是用户的实际场景） |
| 正好等于上限（40 字）不被削；多 1 字（41）只留 40 | ✅ |
| 保存链路照常（没被上限弄坏） | ✅ 列表多一条 |
| 控制台零 error / 零 pageerror | ✅ |

**⚠️ 这一轮又学到一条：`maxLength` 是「输入时拦截」，不是「保存时校验」。**

我原本断言"程序化塞 200 字会触发 `tooLong`、 `checkValidity()` 返回 false"——**实测返回 true、提示为空**。
原因：HTML 规范里 `tooLong` 约束**只对"用户编辑过的值"生效**（dirty value flag），程序化赋值不置这个标志。

⇒ **别拿 `checkValidity()` 去测 `maxLength`，会得到假通过。** 要验就用真实键入或粘贴。
（这条和前面「原生气泡不是 DOM 文本、`checkValidity()` 才是判据」那条**看起来相反，其实互补**：
原生 `required` 是**状态**，`maxLength` 是**行为** —— 状态可以查，行为必须用真实输入触发。）
