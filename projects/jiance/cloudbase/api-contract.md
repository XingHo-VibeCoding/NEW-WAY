## 二、通用约定（每个接口都适用，后面不再重复）

| 项目 | 约定 | 理由 |
|---|---|---|
| **BASE** | `https://{环境ID}.{地域}.app.tcloudbase.com` | Day 15 起可用。正式上线换自定义域名后只改这一处 |
| **编码** | 请求与响应都是 UTF-8；请求头 `Content-Type: application/json` | 避免中文（分类名、备注）变问号 |
| **字段名** | **一律照 `TECH_DESIGN.md` 第五节，不改名、不加新名**<br>**（唯一例外见下方注）** | 前端已经按这些名字在算，改名等于把前端改一遍 |
| **日期** | 文本 `YYYY-MM-DD`（例 `2026-09-20`）；时间戳用 ISO 文本 `2026-09-20T12:01:03.221Z` | 抽屉只认文字，这条对后端同样成立（TECH_DESIGN 5.4） |
| **金额** | 数字，**正数**，最多两位小数，**且不超过 `9999999999.99`**<br>（收入 / 支出靠 `type` 区分，不靠正负号） | 前端现有的记账与统计逻辑就是这么算的。**上界的理由见下方注** |
| **`type` 取值** | 中文 `"收入"` / `"支出"`（**不许改成 `income` / `expense`**） | 前端单选框的 value 就是中文，改了等于前后端各说一门话 |
| **`id`** | 文本，前缀区分表：流水 `ex_` / 经历 `en_` / 匹配 `ma_` | 混在一起时一眼能认出是哪张表的 |
| **成功响应** | **统一套壳**：`{ "ok": true, "data": ... }`，`data` 就是数据本体（对象或数组）<br>**（Day 17 拍板，理由见下方注）** | 前端只需判断一处 `ok`，成功与失败形状对称，不用记两套规则 |
| **失败响应** | 非 2xx + 统一错误体（见下），同样套壳，`data` 恒为 `null` | 前端只需写一处错误处理 |

> **「不改名、不加新名」的唯一例外：单行表携带固定 `id`**（Day 17 补记）
>
> `profile` 是单行表，全库永远只有 1 条，所以它的 `id` 是一个**固定常量**（`profile_singleton`），
> 不是用户数据、也不是新造的业务字段。带上的理由：前端能据此确认「读到的是那唯一一行」。
> 见第五节第 11 条的示例与说明。
>
> **这条例外只对「固定值的 `id`」成立**，不适用于任何其它字段：
> 凡是**用户填的**数据，仍一律照`TECH_DESIGN.md` 第五节，不改名、不加新名。
> （写在这里是为了以后有人再看到 `profile` 返回 `id` 时，不必重新怀疑一遍是不是违约。）

> **为什么 Day 17 改口径**（原来写的是「成功直接返回数据本体，不套外壳」）：
> 换的时候全项目只有 `GET /api/health` 一个函数要跟着改，而第 3 周一共要写 **8 个**业务接口。
> 「中途换格式最贵」—— 等写到第 5 个再换，前端已经按旧格式写了 4 处解析，全得回头改。

### 金额的上界 `9999999999.99`（v1.5 补记，Day 18 写接口落地时加）

> **上界不是随便定的，它就是数据库列的定义。**
> `db/schema.sql` 里`amount` 是 `numeric(12,2)` —— 12 位有效数字、其中 2 位在小数点后，
> 所以整数部分最多 10 位，最大就是 `9999999999.99`。
> **代码里的上界必须 ≤ 数据库列的上界**，否则就变成让数据库来报错了。
> ⚠️ **改 `schema.sql` 改了 `amount` 的类型，这里的上界必须同步改。** 两边要一起改。

**为什么要有上界（Day 18 实测踩出来的）**：

一开始只校验「大于 0」和「最多两位小数」，没管上界。用户传 `10000000000`（1e10）
会被放行 → 真库执行 INSERT → `numeric(12,2)` 装不下 → 数据库报 `numeric field overflow`
→ 网关包成 400 → 接口只能回 **503「数据库暂时连不上，稍后重试」**。

**这个结果特别坏，因为它是永久性错误**：金额填大了，改小就好，
但用户看到的是「稍后重试」，**点一万次也永远不会成功**，
最后多半以为记账功能坏了而放弃。**把「你填错了」报成「稍后重试」是在浪费用户的时间。**

所以服务端在门口就拦：超上界回 **400 / `field: "amount"`**（见第五节第 4 条）。
边界值 `9999999999.99` **放行**（不是 `9999999999.98`）。

> 📌 **一个容易连带踩的坑（Day 18 修 bug 时才发现的）**：
> 加了上界之后，「最多两位小数」那个校验在**大额**上会失效 ——
> 浮点数 `9999999999.99` 乘 100 再乘一个 `1e8` 会**超出 double 的有效位**，
> 精度反而被弄坏，于是这个**合法的上界值被自己的校验判成三位小数而拒绝**。
> 「一个上界值都不让填，比没有上界更糟」——
> 用户填到最大额度被拒，而提示还说「金额最多两位小数」，完全指错方向。
> 现在的写法按**量级**给容差（`Number.EPSILON`）而不是固定小数，
> 细节见 `functions/expenses/index.js` 的 `validateExpenseInput()`。
> **写在这里是为了提醒：以后动金额校验，两件事要一起验** ——
> 「上界值放行」与「真三位小数被拦」。

### Day 17 部署路径调整：第 2/11 号接口改走 HTTP API（v1.4 补记）

> **这一小节只说明「服务端怎么把数据取回来」，不涉及任何对外约定。**
> 下面第二节那张约定表、第五节每个接口的入参 / 出参 / 状态码 / 错误码，
> **在这次调整里一个字都没有改**。前端不需要改任何代码。

**改的是什么**

| 项| 调整前（Day 17 白天） | 调整后（Day 17 部署当天） |
|---|---|---|
| 取数方式 | 云函数用数据库驱动（`pg`）走 **PostgreSQL 协议 TCP 直连** | 云函数用 **CloudBase PostgreSQL HTTP API**（PostgREST 风格） |
| 需要的配置 | `PGHOST` `PGPORT` `PGDATABASE` `PGUSER` `PGPASSWORD` 五个环境变量 | `TCB_ENV`（环境 ID）+ `TCB_TOKEN`（访问令牌，选填） |
| 是否要数据库账号密码 | **要**（`PGUSER` / `PGPASSWORD`） | **不要** |
| 外部可见行为 | 见上表 | **完全不变** |

**为什么改**（这是平台限制，不是代码偏好）

用户用的是 CloudBase **个人版**，该套餐不提供数据库连接地址，
社区 issue #1237 的官方回复原话是「在你当前的个人版套餐下，
就算把这四个值全部填对，TCP 直连也连不上，建议不要在这条路上继续投入」。
→ TCP 直连这条路在个人版下走不通，继续在它上面投入是白费力气。

改用 HTTP API 的依据是官方文档
（`docs.cloudbase.net/database/postgresql/http/query` 与 `.../connecting-to-postgresql`）：

- 基础语法原文：`GET https://<envId>.api.tcloudbasegateway.com/v1/rdb/rest/:table`，
  请求头 `Authorization: Bearer <access_token>`
- 原文：「PostgreSQL 数据库的 HTTP API 基于 PostgREST 协议，查询语法与 PostgREST 完全兼容」
- 原文：「`<token>` 可以是登录后获取的 `access_token`、Publishable Key 或 API Key」

**关键点：这条路不需要数据库账号密码。**
`Publishable Key` 是控制台直接生成的一串访问令牌，不是数据库账号、不用申请——
这正是它绕开个人版限制的原因，也是接口能继续部署的前提。

**因此本节约定以下几条继续成立（逐条核对过，未受影响）**

| 本节约定 | 在新路径下怎么满足 |
|---|---|
| 字段名不改编、不加新名 | 数据库访问收敛在单一函数内，返回值逐字段翻译，**对外字段一个没动** |
| 日期是文本 `YYYY-MM-DD` | 直接透传，**不转成 JS Date 对象**（转了前端的字符串比较全废） |
| 金额是数字、正数 | 底层是 `numeric`，返回时统一过 `Number()`，对外一定是 JSON 数字 |
| `type` 是中文 | 查询条件里传的就是「收入」/「支出」本身（URL 编码后传输） |
| 503 不回传原始报错 | HTTP 网关的响应体**可能含表结构、列名**，所以一概不回传、也不入日志，只记状态码 |

> **一句话给前端看**：这次改的是「后端拿数据的方式」，
> 不是「接口长什么样」。你的 `fetch()` 调用、解析逻辑、字段名、错误处理**都不用动**。

### 统一错误体

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "bad_request",
    "message": "金额必须是大于 0 的数字",
    "field": "amount"
  }
}
```

> 成功与失败**形状对称**，永远是这三个字段（`ok` / `data` / `error`）：
> 成功时 `data` 有值、无 `error`；失败时 `data` 恒为 `null`、`error` 有值。
> 前端只要判断 `ok` 一个字段，再按需读 `data` 或 `error`，不必到处判空。

`code` 取值表（**前端按 code 分档翻译成人话，不要直接把原始报错甩给用户** —— AGENTS.md 附三第 6 条）：

| HTTP 状态码 | `code` | 什么时候 |
|---|---|---|
| 400 | `bad_request` | 参数缺失 / 格式不对 / 超出上下限（带 `field` 定位到具体输入框） |
| 404 | `not_found` | 按 `id` 找不到这条记录（Day 22 起第 5/6 号接口正式用上它，见下方「目标记录不存在」） |
| 405 | `method_not_allowed` | 方法不对（例如对只读接口发 POST —— `POST /api/expenses` 见第 4 条） |
| 409 | `duplicate_submission` | **同一笔重复提交**（Day 18 新增：第 4 号接口同一个 `clientToken` 第二次到达。<br>**不带 `field`** —— 这不是「你填错了」，不该标红任何输入框） |
| 500 | `internal_error` | 服务端自己出错（前端只显示「服务出了点问题，稍后再试」） |
| 503 | `service_unavailable` | 上游通道不可用：**AI 接口调用失败 / 数据库连接失败**（Day 17 补记：原先只写了「AI 接口用」，但第 2/11 号接口连不上数据库时同样回这个码，见第五节第 2 条） |

### 「目标记录不存在」与「查询失败」必须分开（v1.6 补记，Day 22 改删接口落地时立）

凡是**按 id 去改 / 删**的接口，都要面对同一个问题：**给我的这个 id 到底在不在？**
这里有一条**硬口径**，第 5/6 号接口（以及将来的第 9/10/15 号）都要守：

| 服务端遇到的情况 | 必须回 | 含义 |
|---|---|---|
| 查询**成功**，结果为「没有这一条」 | **404 / `not_found`** | **确定它不在** |
| 查询**失败**（网络 / 令牌 / 权限 / 超时 / 网关 5xx） | **503 / `service_unavailable`** | **不知道它在不在** |

> ⚠️ **绝对不许把「查询失败」也回成 404。**
>
> 后果链条（写下来防止后来的人「简化」掉这一层）：
> 数据库抖了一下 → 用户看到「没找到这一笔账」→
> 他以为记录没了 / 以为删掉了 → **很可能重新记一笔** → **多出一条重复账目**。
> 而正确回法（503「稍后重试」）只需要用户点一下重试。
>
> **把「不确定」翻译成「确定没有」，是在制造用户看不见的脏数据。**

> 实现上为什么这需要**一次额外的查询**：网关不会告诉我们「更新/删除了 0 行」
> 还是「请求本身失败」——它只给状态码。所以服务端在动手之前先查一次，
> 用**返回值是不是 null** 来区分「确定不存在」（→404）
> 与**抛异常**区分「不知道」（→503）。
> 多一次往返换来的是「说的和做的一致」，对改和删尤其值得。

> **为什么 409 不并进 400**（前端要区别对待，Day 18 补记）：
>
> | | 400 `bad_request` | 409 `duplicate_submission` |
> |---|---|---|
> | 语义 | 「你填错了，改一下」 | 「**已经存过了**」 |
> | 前端怎么做 | 读 `field`，给对应输入框加 `aria-invalid`，引导用户改 | **不标红任何输入框**，弹一句「已经记过了」然后刷新列表 |
> | 用户要做的动作 | 改正后再提交 | **什么都不用做** |
>
> 混成 400 的后果：前端会去标红一个**本来没错**的表单，
> 用户反复检查自己填的金额、日期、分类，**永远找不到自己哪里填错了**
> ——因为根本没填错，是服务端告诉它「已经存过了」。
>
> 前端只要照旧先判 `res.ok` / `statusCode`，再按 `code` 分支即可，**不用额外处理**。
> `message` 已由服务端写成中文（见第五节第 4 条），前端可直接展示。

`field` 只在「某个输入框填错了」时出现，前端拿它给对应输入框加 `aria-invalid`。

> **`field` 的两个新取值**（v1.5 补记，Day 18）：
>
> | `field` | 什么时候出现 | 说明 |
> |---|---|---|
> | `body` | 请求体不是合法 JSON、或不是一个 JSON 对象 | **不是某个输入框**，是「整个请求体」坏了。挂到 `date` 上会让前端去标红日期框，用户完全看不懂哪里错了 |
> | `clientToken` | 传的 `clientToken` 格式不合法（见第五节第 4 条的白名单） | **刻意不静默忽略**：悄悄换成服务端自增会让用户以为防住了（其实没防住） |
>
> ⚠️ **这两个都只是把「原来会掉进 500 的情况」显式化，不新增任何状态码** ——
> 状态码仍然是 400，仍然是 `code: "bad_request"`，仍然带 `field`。
> 「请求体解析失败」如果不登记，前端就只能拿到一个 500 而无从判断该怎么办。

> | 1 | 环境变量 `TCB_ENV` 已配（环境 ID） | **503**，日志写「运行配置缺失：缺少环境变量 TCB_ENV」 |

### 4. `POST /api/expenses` — 记一笔

**请求体**

```json
{
  "date": "2026-09-30",
  "amount": 38.5,
  "type": "支出",
  "category": "餐饮",
  "note": "楼下快餐"
}
```

`id` / `createdAt` / `updatedAt` **由服务端生成**；前端即使传了也忽略（不让前端决定 id，否则可能撞号）。

**成功 201**：返回新建的**完整对象，8 个字段齐全**（形状同第 2 条里的一项）：

```json
{
  "ok": true,
  "data": {
    "id": "ex_a1b2c3d4e5f6g7h8",
    "date": "2026-09-30",
    "amount": 38.5,
    "type": "支出",
    "category": "餐饮",
    "note": "楼下快餐",
    "createdAt": "2026-09-30T08:12:03.221Z",
    "updatedAt": "2026-09-30T08:12:03.221Z"
  }
}
```

> **为什么强调「8 个字段齐全」**：前端「记完一笔立刻把这笔显示在列表里」时，
> 会把响应里这个对象**直接追加**到 `GET /api/expenses` 读回来的列表中。
> 只要字段形状一致，前端就不用写第二套取值代码。
> 所以**服务端宁可回 503，也不把一个缺字段的对象交给前端** ——
> 那一笔是真的写进库了，回一个残缺对象会导致
> **界面显示成「undefined 元」而数据库里有这笔账，界面与数据永久对不上**，
> 而且接口回的是 201「成功」，任何地方都查不出错误。
> 📌 因此：网关返回的记录不完整 / 不是对象时，服务端回 **503**，不返回残缺数据。

#### 请求体可选字段：`clientToken`（防重复提交，Day 18 新增）

**它是什么**：客户端在**每次点提交时生成的一个一次性随机串**，
和上面的业务字段一起发过来。服务端拿它拼主键：`id = "ex_" + clientToken`。

**为什么要它**：网络卡住时用户以为没点上，手快点两下「保存」，
两次 POST 内容一样，数据库就多出一笔重复账目 ——
月度合计多算一笔，月底对账对不上，而且**用户完全看不出来**。
把令牌编进主键之后，同一个令牌提交两次 → 主键相同 → 数据库拒绝 →
第二次被拦成 409。**防重靠的是数据库的唯一约束，不是前端的节流。**

| 项 | 内容 |
|---|---|
| 是否必填 | **选填**。**不传也能记成功**，但见下方「必须诚实说明的前提」 |
| 格式白名单 | `^[A-Za-z0-9_-]{8,40}$` —— 只允许字母、数字、下划线、连字符，长度 8~40 |
| 格式不合法 | **400 / `code: "bad_request"` / `field: "clientToken"`** |
| 示例 | `"a1b2c3d4e5f6g7h8"`（16 位随机串即可） |

> ⚠️ **必须诚实说明的前提：不传 `clientToken` 就没有防重。**
>
> | 情况 | 行为 | 防重 |
> |---|---|---|
> | 带了合法的 `clientToken` | `id = "ex_" + clientToken` | **生效** —— 同令牌第二次提交回 409 |
> | **没传 / 传空串** | 服务端**自增**一个 id，并在日志里打一条警告 | **不生效** —— 手快点两下会真的记两笔 |
> | 传了但格式不合法 | 回 400 | —— |
>
> 令牌是**客户端生成的**，服务端拿不到就造不出来，所以「不传」只能是「没有防重」，
> 服务端**不拒绝**这次提交（用户记账的心愿不该因为一个防重参数被拦下）。
> **唯一的解法是前端每次点提交都带上 `clientToken`。**
> 那条日志警告是**防重失效的告警**（不是随手打的日志）——
> 线上频繁出现就说明前端某个版本没在传令牌，该去查前端了。
>
> **不要试图「修」主键的大小写问题**：PostgreSQL 文本主键**区分大小写**，
> 所以 `Day18Token01` 与 `day18token01` 是两个不同令牌、算两次提交。
> 这是主键机制本身的固有边界，责任在**前端每次生成随机令牌**（不要用可预测的固定串）。

**错误**

| 状态码 | 触发条件 |
|---|---|
| 400 | `date` 格式不对 / `amount` 不是大于 0 的数字、超过两位小数、**或超过上界 `9999999999.99`**（第二节） / `type` 不是 `收入` 或 `支出` / `category` 不在该 `type` 对应的选项里 / `clientToken` 格式不合法 |
| 405 | 用了 `PUT` / 其它方法。**注意**：`DELETE` 自 v1.6（Day 22）起**不再是 405** —— 它是第 6 号接口，已实现。改一笔/删一笔请用**带 `:id` 的地址** + `PATCH` / `DELETE`（见第 5/6 条） |
| 409 | **同一笔重复提交**（同一个 `clientToken` 第二次到达 → 主键冲突）。`code: "duplicate_submission"`，**不带 `field`** |

> **400 必带 `field`，409 不带** —— 这是有意的区别：
> 400 是「某个输入框填错了」，前端要靠 `field` 标红对应输入框；
> 409 是「已经存过了」，**没有任何输入框需要标红**，
> 前端弹一句「已经记过了」然后刷新列表即可。理由见第二节状态码表。
>
> **503** 也会回：数据库连不上、令牌权限不足、写入超时等（与第 2 条同一套分档处理）。

**分类合法值**（照现有代码）：

- 支出：餐饮 / 交通 / 房租 / 购物 / 医疗 / 娱乐 / 其他
- 收入：工资 / 兼职 / 理财收益 / 其他

### 5. `PATCH /api/expenses/:id` — 改一笔

> ⚠️ **方法名 v1.6 由 `PUT` 更正为 `PATCH`。** 这是一次**更正**而不是新增能力：
> 本条正文从 Day 15 起写的就是「只传**要改的字段**即可（**部分更新**）」——那是 PATCH 的定义；
> 而 `PUT` 在 REST 里是「**整条替换**」（没传的字段会被清空/重置）。两者名实不符。
> Day 22 实现时拍板：**改名字去符合正文**，而不是改正文去迁就一个错名字。
> 影响：本条此前一直是占位（调用回 405），**前端没有任何已有代码按 PUT 写过**，所以不构成破坏性变更。

| 项 | 内容 |
|---|---|
| 路径参数 | `:id` |
| 请求体 | 只传**要改的字段**即可（部分更新），例 `{ "amount": 42, "note": "加了个蛋" }` |

**可改字段（只有这 5 个）**

| 字段 | 规则 | 与第 4 条（记一笔）是否一致 |
|---|---|---|
| `date` | `YYYY-MM-DD`，且**必须是日历上真实存在的一天** | ✅ 完全一致 |
| `amount` | 数字，> 0，最多两位小数，上界 `9999999999.99` | ✅ 完全一致 |
| `type` | 只能是 `收入` 或 `支出` | ✅ 完全一致 |
| `category` | 必须属于**该 `type` 对应**的那一组分类 | ✅ 完全一致 |
| `note` | 文字，最多 50 字；不传 / `null` / `""` 都表示「没备注」 | ✅ 完全一致 |

**不可改字段（服务端掌管，前端传了也忽略，不报错）**

| 字段 | 为什么 |
|---|---|
| `id` | 改主键不是「改一笔账」，是「换一条账」 |
| `createdAt` | 创建时间是一次性事实，没有「修改」一说 |
| `updatedAt` | **由服务端强制刷新**为本次修改的时间（契约要求，不接受前端传值） |

**成功 200**：返回更新后的完整对象（8 个字段，与第 2 条里的一项形状**完全一致**），`updatedAt` 已刷新。

```json
{
  "ok": true,
  "data": {
    "id": "ex_1758200000000_ab12",
    "date": "2026-09-03",
    "amount": 42,
    "type": "支出",
    "category": "餐饮",
    "note": "加了个蛋",
    "createdAt": "2026-09-03T02:00:00.000Z",
    "updatedAt": "2026-10-10T06:00:00.000Z"
  }
}
```

> **为什么 `data` 里必须字段齐全**：前端「改完立刻把这一条更新到列表里」时，
> 塞进列表的对象和第 2 条读回来的必须是**同一个形状**。
> 网关若回了一份残缺对象，服务端**回 503 而不是把残缺对象交给前端** ——
> 否则前端的列表会显示成 `undefined 元`，而数据库里明明是好的（界面与库永久不一致）。

**错误**

| 状态码 | 触发条件 |
|---|---|
| 400 | 请求体不是 JSON 对象 / **没有要修改的内容**（空对象、或所有字段都没传） / `date` 格式不对或日期不存在 / `amount` 不是大于 0 的数字、超过两位小数、超过上界 / `type` 不是 `收入` 或 `支出` / `category` 不在该 `type` 对应的选项里 / `note` 超 50 字或非文字 |
| 400 | **`type` 改了但 `category` 跟着不合法**（见下方「两个必须知道的组合」） |
| 400 | **提交的值与库里完全相同**（改了等于没改，见下方） |
| 404 | `id` 不存在 → `code: "not_found"`，`message: "没找到这一笔账，可能已经被删掉了"` |
| 405 | 用了其它方法 |
| 503 | 数据库连不上 / 令牌权限不足 / 写入超时（与第 2/4 条同一套分档） |

> **两个必须知道的组合**（Day 22 实现时踩实的两处，新写的客户端请照着处理）

**① `type` 与 `category` 是咬合的 —— 只改 `type` 可能连带把 `category` 弄成非法**

数据库有一道约束：`餐饮` 只能配 `支出`，`工资` 只能配 `收入`。
于是「把一笔支出改成收入、但分类还留着餐饮」是个**非法组合**。

服务端的处理是：**先把这一条读出来，把改动合并上去，校验「改完之后」的那个整体**。
所以这种情况下会回：

```json
{ "ok": false, "data": null,
  "error": { "code": "bad_request",
             "message": "类型改成了「收入」，分类也得跟着改。收入只能用：工资、兼职、理财收益、其他",
             "field": "category" } }
```

⚠️ 这条 message **会列出新类型可用的分类**，不是干巴巴一句「不匹配」——
因为后者会让用户反复试错。前端直接把 message 显示出来即可。

**② 「改了等于没改」回 400，不回 200**

如果提交的值和库里现在的一模一样（比如用户把每个字段都改回原样），服务端回：

```json
{ "ok": false, "data": null,
  "error": { "code": "bad_request",
             "message": "填的内容和原来一样，没有需要修改的地方",
             "field": "body" } }
```

> **为什么不是 200**：回 200 的话，用户点「保存」看到「改好了」，
> 而实际什么都没发生 —— **界面在说谎**。宁可明说「没有需要修改的地方」。

> **服务端实际只发「真正变了的字段」**（这是 PATCH 的意义，不是优化）：
> 前端把整张表单一起发过来是常态，服务端会逐字段比对，
> **值没变的一律不写库**。这样并发下不会「把别人刚做的修改覆盖回去」（丢更新）。
> 唯一例外是 `updatedAt` —— 它由服务端每次都刷新。

**503 的特别提醒（改删都适用）**

> ⚠️ **「这一条查不到」与「查询本身失败」必须分开处理，绝不能混**：
>
> | 情况 | 返回 | 为什么 |
> |---|---|---|
> | 服务端正常查到「没有这一条」 | **404** | 确定不存在 |
> | 查询过程出错（网络 / 令牌 / 权限 / 超时） | **503** | **不确定**它在不在 |
>
> 把后者也回成 404 的后果：数据库抖一下 → 用户看到「这笔不存在」→
> 他很可能会**重新记一笔** → **多出一条重复账目**。而那个 503 本来点一下「重试」就好。
> **「不确定」绝不能被翻译成「不存在」。**

### 6. `DELETE /api/expenses/:id` — 删一笔

| 项 | 内容 |
|---|---|
| 路径参数 | `:id` |
| 请求体 | **无**。删除只靠地址里的 `:id` 定位 |

**成功 200**

```json
{ "ok": true, "id": "ex_1758200000000_ab12" }
```

> ⚠️ **成功体只有 `ok` 与 `id` 两个字段，没有 `data`**（本条从 Day 15 起就是这么写的，Day 22 未改）。
> 这是**刻意**的：删除没有「要交给前端的对象」，前端要的就是「把它从列表里去掉」。
> 返回被删掉的那一行反而会诱使人写成「把返回值塞回列表里去更新」——
> 而正确写法是**从列表里移除**它。**返回形状会引导前端的正确写法。**

**错误**

| 状态码 | 触发条件 |
|---|---|
| 400 | 地址里没有 `:id`，或 `:id` 形状不对（不是 `ex_` 开头的字母数字） |
| 404 | `id` 不存在 → `code: "not_found"` |
| 405 | 用了其它方法 |
| 503 | 数据库连不上 / 令牌权限不足（**删除最可能**：令牌角色没有 DELETE 权限）/ 超时 |

> **删除幂等**：已删过的再删，仍返回 **404**，**不要回 500**（本条从 Day 15 起就写死了）。
> 404 在这里的含义是「你问的这条现在不在」，是**如实回答**，不是错误 ——
> 前端拿它去「刷新列表」即可。

> ⚠️ **服务端在真正删除之前会先查一次「这一条在不在」**（这正是上面那条 404 的来源）。
> 代价是多一次数据库往返，换来的是**删除不会误报**：
> 「不确定」回 503、「确定不在」回 404，两者绝不含糊。
> 删除是整个项目里**唯一不可逆的操作**（新增错了能删、改错了能再改，删错了只能凭记忆重记），
> 所以在这里多花一次往返是划算的。

> **为什么服务端不核对「删掉了几行」**：那需要让网关返回被删的行，
> 而**网关不保证认 `DELETE` 上的 `Prefer` 头**。若它不认而响应恰好是空的，
> 我们会把「真删掉了」误读成「没删到」→ 回 404 →
> 用户以为记录还在、可能重新记一笔，**而那条其实已经删了**。
> 宁可多一次往返，也不赌网关的行为。

> 前端有「删除前先问一次 + 6 秒内可撤销」，撤销依赖 `pendingUndo`；后端不做回收站（第 3 周范围外）。
> **「删除前问一次」是前端的事，后端不管** —— 分工明确：后端保证「说的和做的一致」，前端保证「用户点之前想清楚」。
