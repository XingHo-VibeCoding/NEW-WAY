## 五-0. ⚠️ 部署前必读：为什么改走 HTTP API（v1.14 已改）

**结论先说**：TCP 直连这条路在个人版下走不通，今天已经**改走 CloudBase PostgreSQL HTTP API**，
把那个限制**绕开**了。下面解释为什么，以及代价是什么。

### 为什么不能继续用数据库直连

用户用的是 CloudBase **个人版**，该套餐**不提供数据库连接地址**。三条常规路径全部封死：

| 路径 | 状态 | 依据 |
|---|---|---|
| 内网地址（VPC） | ❌ 个人版**没有「内网互联」开关** | 社区 issue #887 / #888 / #978 多个先例一致 |
| 公网直连 | ❌ 要配安全组，安全组需**独享集群**；共享集群下开关开不了 | 你在 issue #1236 已实测过 |
| 同 VPC 的 CVM | ❌ 数据库在平台共享集群里，不通 | 社区回复 |
| 云托管（CloudBase Run） | ❌ **社区已证实走不通**，官方回复原话：「在你当前的个人版套餐下，就算把这四个值全部填对，TCP 直连也连不上，建议不要在这条路上继续投入」 | 社区 issue #1237 |

> 上表保留是为了说明「为什么换路」，不是给出选项。**今天不要再在 `pg` 直连上投入时间。**

### 现在走哪条路：HTTP API

官方文档 `docs.cloudbase.net/database/postgresql/http/query` 的**基础语法原文**：

```
GET https://<envId>.api.tcloudbasegateway.com/v1/rdb/rest/:table

Authorization: Bearer <access_token>

Content-Type: application/json
```

同一份文档里另外两句原文，是这条路能走通的关键：

> 「PostgreSQL 数据库的 HTTP API 基于 **PostgREST 协议**，查询语法与 PostgREST 完全兼容。」

> 「`<token>` 可以是登录后获取的 `access_token`、**Publishable Key** 或 API Key。」

**⭐ 最重要的一点：这条路不需要数据库密码。**

`Publishable Key` 是控制台直接生成的一串访问令牌 —— 它**不是数据库账号**，
不用申请数据库账号密码，不会因为「个人版没有数据库连接信息」而卡住。
这正是它能绕开上面那个限制的原因。（API Key 权限更大，官方明确说不能暴露在前端；
云函数在后端其实也能用，但 Publishable Key 最省心、不用处理过期，所以当默认值。）

### 改造动了什么、没动什么

| | 改造前 | 改造后 |
|---|---|---|
| 取数方式 | `pg` 驱动，PostgreSQL 协议 TCP 直连 | HTTPS 请求，PostgREST 风格查询 |
| 环境变量 | 5 个 `PG*` | `TCB_ENV`（+ 可选 `TCB_TOKEN`） |
| npm 依赖 | 依赖 `pg` | **零依赖**（用 Node 18 自带的 `fetch`） |
| 要数据库密码吗 | 要 | **不要** |
| **对外接口行为** | 见契约第五节第 2/11 条 | **完全不变** |

> **前端不受影响**：字段名、排序规则、状态码、错误码、错误体形状，一个字都没改。
> 变的只是「服务端怎么把数据取回来」这一层。
>
> 改造之所以便宜，是因为两个文件早就把数据库访问收敛在了**各1 处**：
> ```
> expenses/index.js:313   全文仅 1 处 pool.query
> profile/index.js:262    全文仅 1 处 pool.query
> ```
> 参数校验、套壳（`json`/`ok`/`fail`）、错误处理、字段映射（`toFrontend`）
> **全部与数据库无关**，原样保留。

### ⚠️ 这个改动带来的、必须部署后现场验的三件事

PostgREST 的查询语法**不是 SQL**，改写后有三处不能想当然。代码里已按文档写好，
但**「CloudBase 网关是否真的认这些写法」只能在部署后真跑一次**才算证据：

| # | 待验什么 | 期望 | 不对说明什么 |
|---|---|---|---|
| 1 | **text 字段的前缀匹配**：`date=like.2026-09%` | `?month=2026-09` 返回 **5 条** | 网关可能不认`like` 的 `%`，或解码方式不同 → 改用范围查询 `date=gte.2026-09-01&date=lt.2026-10-01` |
| 2 | **多列排序**：`order=date.desc,created_at.desc` | 第一条 `2026-10-01`、最后一条 `2026-09-01` | 网关可能只认单列 → 拆成两次查询或改用别的表达 |
| 3 | **`numeric` 序列化**：`amount` 是 JSON 数字还是字符串 | 契约要求是**数字** | 网关可能返回 `"1500.00"` —— 代码里的 `Number()` 已能兜住，**这一项不影响正确性**，只需确认 |

> 第3 项**代码层面已经安全**（`Number()` 对数字和字符串都正确，本地两种都验过）。
> 但仍要人眼确认一次，因为 api-contract 第二节要求「金额是数字」，
> 而网关的实际行为只有部署后才知道。
>
> 验证步骤见第五节之三的验证点 2 与验证点 4。

## 五-1. 第 1 步：抄下环境变量

两个云函数**各配这 1~2 个环境变量**（v1.14：不再是 5 个 `PG*`）。
**抄在纸上，不要写进代码、不要提交**（AGENTS.md 第五节第 3 条）。

| 变量 | 必填？ | 含义 | 去哪抄 |
|---|---|---|---|
| `TCB_ENV` | **必填** | **环境 ID**。代码用它拼出基础域名 `{TCB_ENV}.api.tcloudbasegateway.com` | 控制台首页左上角，或「环境设置」→「基础信息」→ **环境 ID** |
| `TCB_TOKEN` | 选填 | **访问令牌**。代码放进`Authorization: Bearer <令牌>` 请求头 | 控制台 →「安全」→「身份认证」→ **访问令牌 / 令牌管理** → 新建，取 **Publishable Key**（或 API Key） |

> **`TCB_ENV` 就是环境 ID**，形如 `maybe666-d6g1z4erj391b54f5`。
> 它和「HTTP 访问服务域名」「静态托管域名」不是一回事：那两个域名带地域/APPID 后缀，
> 只有环境 ID 是纯 ID。
>
> **`TCB_TOKEN` 不填也能跑**：代码会自动走「匿名登录」换一个临时 `access_token`
> （2 小时有效，自动缓存并提前刷新）。但**推荐填上Publishable Key** ——
> 不会过期、省一次往返、行为更可预测。

### ⚠️ 三个最容易搞错的地方

1. **不再需要数据库账号密码**。v1.13 版本的 `PGUSER` / `PGPASSWORD` 已全部作废 ——
   那两个是**数据库自己的账号**，而这条路用的是**平台访问令牌**，不是一回事，别混。
2. **`TCB_TOKEN` 是密钥**。别写进代码、别提交到仓库、别截图。
   代码里**多处 `process.env` 全是读取、无一处赋值**（保持原样）。
3. **`TCB_TOKEN` 不是 `publishableKey` 吗？** 前端项目里那个 key 和这个**可能**是同一个值，
   但它们**用途不同**：前端那个是给浏览器用的，这里是给云函数用的。
   抄的时候看清自己在哪个控制台页面，别抄错成 AppID 或 SecretId。

> 若日志里有 `[profile] ...` 任何一行，说明路由是通的，问题在别处。
>
> **修法**：函数详情 → 域名管理 → 触发路径填 `/api/profile` → 保存 → **等 3–5 分钟**。
> 然后到「HTTP 访问服务 → 路由管理」确认**两行都在**。
>
> ### ⚠️【Day 19 踩坑】两个函数认的令牌变量名**不一样**，别照抄错

> | 函数 | 认哪些变量 | 用途 |

> Publishable Key 控制台「安全 → 身份认证 → 访问令牌 / 令牌管理」里新建（以 `eyJ` 开头那串）。
> 只有 `expenses` 要写接口时才需要额外配 `CLOUDBASE_APIKEY`。
>
> ### ⚠️【Day 19踩坑】环境变量是**每个函数独立**的，不共享
>
> 新建 `profile` 后，`expenses` 那边配好的变量**不会自动带过来**。

> 看到这个就补 `TCB_ENV`（值 = 你的环境 ID）。
>
> ### ⚠️【Day 19 踩坑】传zip 可能不动环境变量，但要确认
>
> 重新上传 zip 后**顺手看一眼**「配置 → 环境变量」还在不在。
> 实测这次没被冲掉，但不同平台版本行为可能不同 —— **花 5 秒看一眼，比 503 排查 10 分钟划算。**

> **第 9 步（v1.14 变化）**：以前这步是**必须**的 —— 不点「安装依赖」会因为找不到 `pg` 直接 503。

### 验证点 1 · 先看health（确认通道本身是通的）

### 验证点 2 · 读账目列表

打开：`https://{HTTP访问域名}/api/expenses`

期望（用 seed.sql 的 6 条**假数据**验，金额和备注都是编造的）：

```json
{
  "ok": true,
  "data": [
    {"id":"ex_1759000000000_a006","date":"2026-10-01","amount":1500,"type":"收入","category":"兼职","note":"周末外包小活","createdAt":"2026-10-01T21:00:00.000Z","updatedAt":"2026-10-01T21:00:00.000Z"},
    ... 共 6 条
  ]
}
```

**要亲眼核对这 3 件事**（这是今天最关键的地方）：

| # | 核对什么 | 对的样子 | 错的样子意味着 |
|---|---|---|---|
| 1 | `amount` 是**数字**不是字符串 | `"amount": 1500` | `"amount": "1500.00"` → 说明云端代码不是最新版，重新上传 zip |
| 2 | 排序真的生效 | 第一条是 `2026-10-01`，最后一条是 `2026-09-01` | 顺序乱 → 代码没更新成功 |
| 3 | `note` 处理对了 | 房租那条是 `""`（空字符串，**不是 `null`**） | 显示成 `null` → 代码没更新 |

> **第 1 条为什么这么重要**：`amount` 在数据库里是 `numeric` 类型。
> ⚠️ **v1.14 更新**：以前的说法是「`pg` 驱动交给 JavaScript 时是字符串」——
> 那是**旧 TCP 直连路径**下本地实测的结论（`pg_typeof` 查数据库侧是 `numeric`，
> 驱动读一次拿到 `"38.50"`）。**改走 HTTP API 后，网关怎么序列化 `numeric` 需要重新确认**
> （可能是 JSON 数字 `1500`，也可能是字符串 `"1500.00"`，取决于网关实现）。
>
> **好消息是这一项不影响正确性**：`toFrontend()` 里的 `Number()` 对两种输入都给出同一个结果，
> 本地已两种都真跑验过。所以你看到 `1500` 或 `1500.00` **都算通过**——
> 只要它是**数字类型**、不是带引号的字符串就行。
>
> 但仍要人眼确认一次：契约第二节要求「金额是数字」，
> 而网关的实际行为只有部署后才知道。若看到 `"amount": "1500.00"`（带引号），
> 说明传的是旧版zip，重新上传 `expenses.zip`。

### 验证点 3 · 读个人参数

打开：`https://{HTTP访问域名}/api/profile`

期望：
```json
{
  "ok": true,
  "data": {
    "id": "profile_singleton",
    "savings": 30000,
    "monthlyExpense": null,
    "name": "张三",
    "contact": null,
    "targetRole": "前端工程师",
    "updatedAt": "2026-10-02T10:00:00.000Z"
  }
}
```

要核对：

| 核对什么 | 为什么 |
|---|---|
| `savings` 是**数字** 30000 | 同样是 `numeric`，要`Number()` 转（`"30000.00"` 和 `30000` 都算通过，只要不是带引号的字符串） |
| `monthlyExpense` 是 **`null` 不是 `0`** | null 的含义是「没手填，请前端按近 3 个自然月自动算」。**存 0 会让底牌页「还能撑几个月」那个除法崩掉** |
| `contact` 是 `null` | seed 里**故意留空** —— 真实手机号/邮箱绝不进仓库（AGENTS.md 附三第 3 条）。顺便验证「字段存在但值为 null 时仍返回 200」 |

### 验证点 4 · 筛选参数（余力加练，契约里已登记）

在地址后面加参数，一个一个试：

| 打开什么 | 期望 |
|---|---|
| `?month=2026-09` | **5 条**（10-01 那条被正确滤掉） |
| `?month=2026-10` | **1 条** |
| `?type=支出` | **4 条** |
| `?limit=2` | **2 条** |
| `?month=2026-13` | **400**，报错里带 `"field":"month"` |
| `?type=xxx` | **400**，带 `"field":"type"` |

> ### ⚠️ v1.14：`?month=2026-09` 这一条是**今天最关键的验证点**
>
> 改走 HTTP API 后，按月筛选从SQL 的 `date LIKE '2026-09%'`
> 改成了 PostgREST 的 `date=like.2026-09%`（`%` 经URL 编码后实际发出去是 `%25`）。
>
> **这一条代码层面已按官方文档写好、本地也已真库验过能筛出 5 条**，
> 但「CloudBase 网关是否真的认这个写法」只有部署后才知道。**所以上面第 1 行必须人眼确认。**
>
> | 现象 | 含义 | 怎么办 |
> |---|---|---|
> | 返回 **5 条** |✅ 网关认这个写法 | 正常往下走 |
> | 返回 **6 条**（没过滤） | 网关忽略了 `like` 条件 | 改用范围查询：`date=gte.2026-09-01&date=lt.2026-10-01` |
> | 返回 **0 条** | 网关认 `like` 但解码方式不同 | 同上，改用范围查询（不依赖通配符，最稳） |
> | 返回 **503** | 网关不接受这个查询串 | 看云函数日志里的状态码，对照第六节排错表 |
>
> **备用方案**：`like` 万一不行，用 `gte` + `lt` 的范围查询一定能work ——
> 因为 `date` 是 `'YYYY-MM-DD'` 定长 7 位、字典序等于时间序，
> `>= '2026-09-01' AND < '2026-10-01'` 精确等于「9 月」，而且不依赖任何通配符语义。

400 长这样：
```json
{"ok":false,"data":null,"error":{"code":"bad_request","message":"month 格式必须是 YYYY-MM，例如 2026-09","field":"month"}}
```

> 顺手验一个安全性：`?month=2026-09%27%20OR%20%271%27%3D%271`（SQL 注入尝试）
> **必须返回 400**。本地已实测 7 条注入全在校验层被拦住（连请求都没发出去）。
>
> ⚠️ v1.14 补充：改走 HTTP API 后**没有驱动替我们做参数化**了，
> 现在靠两层防线：① `MONTH_PATTERN` / `VALID_TYPES` 把值限定成确定形状，
> ② 拼 URL 时每个键值都过 `encodeURIComponent`（把 `&` `=` `?` `#` 转义掉）。
> 详见 `index.js` 里 `restUrl()` 的注释。

| POST 写 | 正常 201 / 无note / body 是对象 / body 是 base64 / 空 body / 非法 JSON |
| POST 400 | 日期格式 / 2 月 31 日 / 金额 0 / 负数 / 三位小数 / 超上界 / type 非法 / 分类错配 / 备注超长 / 备注非字符串 / clientToken 格式错 |
| POST 边界 | 浮点噪声 0.1+0.2 **放行** / 上界 9999999999.99 **放行** / 10000000000 拦住 |
| POST 201 出口 | 字段残缺 / 元素是数字 / 空数组 / 不是数组 → 全回 503 |
| 409 防重 | 同令牌两次提交 → 201 然后 409，两次发出去的 id **完全相同** |
| profile | 正常 / 查不到回空对象 / monthlyExpense 为 null / 字符串 / POST → 405 / 四种 503 |

⚠️ **有一件事本地测不出来，别把它当成已验证**：
假网关只能验「我们发出去的请求长这样」和「我们怎么处理返回」，
**验不了 CloudBase 网关认不认**。所以「网关解码后 `%25` 是否还原成 LIKE 通配符」
这类问题，仍须部署后按第五节之 3 的验证点真跑一次。
